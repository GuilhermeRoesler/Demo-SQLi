Demo SQLi — Buscar Herói

Guia passo a passo para entender SQL Injection e a correção com prepared statements. Sem PHP real: as respostas são forjadas para os casos do roteiro.

Uso acadêmico / demonstração. Isto não é um banco nem um servidor PHP — é uma simulação no navegador. Não use estas técnicas contra sistemas de terceiros.

O que é SQL Injection?

Aplicações montam comandos SQL para falar com o banco. Se a entrada do usuário for colada dentro da string SQL, o atacante pode alterar a lógica do comando.

Consulta esperada Filtrar heróis pelo nome digitado, ex.: Batman.
O problema Concatenar a entrada na query transforma dado em código SQL.
A defesa Prepared statements: o valor vai separado do molde SQL.

Neste demo fictício, a versão vulnerável equivale a:

SELECT id, nome_heroi, poder FROM herois WHERE nome_heroi = 'ENTRADA_DO_USUARIO'

Se a entrada for Batman, tudo bem. Se for ' OR '1'='1, a condição muda e o filtro deixa de funcionar como o programador imaginou.

Passo 4 — Prepared statements

Mesmos payloads, modo seguro. A string inteira é buscada como nome, não como SQL — a injeção falha.

Passo 5 — Antes e depois

Trechos equivalentes ao lab PHP deste repositório. A diferença crítica é uma linha: concatenação vs placeholder.

✗ buscar.php (vulnerável)

$sql = "SELECT id, nome_heroi, poder
        FROM herois
        WHERE nome_heroi = '" . $nome_heroi . "'";

$conn->query($sql);

✓ buscar_seguro.php

$stmt = $conn->prepare(
  "SELECT id, nome_heroi, poder
   FROM herois
   WHERE nome_heroi = ?"
);
$stmt->execute([$nome_heroi]);
  • Sei explicar SQLi em uma frase.
  • Vi o bypass (' OR '1'='1) e o vazamento via UNION na simulação.
  • Vi o mesmo payload falhar no modo seguro.
  • Entendi que prepared statements separam dado de código SQL.
